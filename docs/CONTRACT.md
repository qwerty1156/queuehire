# Контракт QueueHire

## Авторизация и данные

Все `/v1/*` требуют действующий `X-API-Key`.
Отсутствующий, неизвестный или отозванный ключ: 401, `invalid_api_key`.
Tenant определяется только ключом, не параметрами клиента.

Читать, изменять, повторять и добавлять заметки можно только своим заданиям.
Чужой ID и несуществующий ID: 404, `job_not_found`, без изменения данных.
Проверка принадлежности выполняется до проверки состояния и баланса.

`/health/live` и `/health/ready` не требуют ключа.
Все обычные ответы содержат `X-Request-ID`.
Формат бизнес-ошибки: `{"detail": "error_code"}`.
Ошибки входных данных Pydantic сохраняют стандартный формат 422.

## Создание

`POST /v1/jobs` принимает JSON с `title` и `text` и заголовок
`Idempotency-Key` длиной 1–100 символов. Дополнительные поля JSON запрещены.
Валидация длины title/text задаётся моделями и должна сохраниться.

Новое задание: 201, `queued`, attempts=0, result=null, error_code=null.
Цена по умолчанию — 3 целых кредита; берётся из `JOB_COST` при создании
и сохраняется в job.cost. Для теста `JOB_COST=3`, `MAX_ATTEMPTS=3`.
Ответ имеет структуру `JobOut` из `app/schemas.py`.

Создание job, уменьшение баланса и ledger charge составляют одну атомарную
операцию. При отказе записи ни один из трёх эффектов не сохраняется.
Баланс не может стать отрицательным. Несколько запросов не могут потратить
одни и те же кредиты. Недостаток средств: 402, `insufficient_credits`.

Идемпотентность ограничена парой `(tenant_id, Idempotency-Key)`:

| Ситуация | Ответ | Эффект |
|---|---|---|
| Первый запрос | 201 | Новое задание и одно списание |
| Тот же tenant, key и payload | 200 | Тот же job ID, текущее состояние, без списания |
| Тот же tenant и key, другой payload | 409 `idempotency_conflict` | Без изменения данных |
| Другой tenant с тем же key | 201 | Собственное независимое задание |

Payload сравнивается по точным значениям title и text; пробелы и регистр
не нормализуются. Порядок полей JSON не влияет на равенство.
Повтор работает и при балансе 0. При конкурентном одинаковом запросе
ровно один ответ 201, остальные 200, ID один, списание одно, без 500.
При конкурентных разных запросах с балансом 3 проходит ровно один;
остальные получают 402. Ключ создания сохраняется после обработки и retry.

## Баланс и ledger

`GET /v1/account` возвращает id, name, balance текущего tenant.
`GET /v1/account/ledger` возвращает только его записи.

Каждая созданная демо-компания имеет запись `opening`.
Charge отрицательный, refund положительный, суммы целочисленные.
Для одного цикла обработки — не более одного charge и одного refund.
Сумма ledger должна совпадать с balance. При ручном повторе появляются
новые записи того же job ID: несколько циклов не считаются дублями.
Как различать циклы внутри базы — твой выбор.

## Worker

Публичный контракт worker для проверки:
`app.worker.process_job(session, job_id)`. Сохрани эту точку входа.
Возвращаемая строка для no-op не оценивается: важны состояние и эффекты.

За один вызов queued job выполняется не более одной попытки.
Attempts увеличивается только при фактически начатой попытке.
Перед внешним вызовом статус становится `running`.
В одном цикле обработки job одновременно может быть только один владелец.
При двух конкурирующих worker успешный провайдер вызывается один раз.
Синхронизация должна работать между процессами, не только через Python Lock.

| Ответ провайдера | Состояние | Кредиты |
|---|---|---|
| Успех | succeeded, result заполнен, error_code=null | Без возврата |
| Временная ошибка, attempts < 3 | queued, error_code сохранён | Без возврата |
| Временная ошибка, attempts = 3 | failed, error_code сохранён | Один возврат стоимости |
| Постоянная ошибка | failed сразу после первой попытки | Один возврат стоимости |

Повторный вызов terminal job (`succeeded`, `failed`) — no-op:
не вызывает provider, не меняет attempts, результат, баланс или ledger.
Вызов уже running job также не запускает вторую обработку.
Неизвестный ID не создаёт данные и не вызывает provider.
Все изменения финального состояния и refund атомарны.

Внешний вызов выполняется через `app.worker.analyze`; эта ссылка используется
тестом для замены provider. Не убирай возможность подмены в тестах.
Реальная сеть не нужна. Маркеры провайдера описаны в исходном модуле:
`[FAIL_ONCE]`, `[TEMPORARY]`, `[PERMANENT]`.

Восстановление job после аварийной смерти running worker — вне обязательного
контракта. Не заявляй, что оно работает, без отдельного подтверждения.

## Ручной повтор

`POST /v1/jobs/{job_id}/retry`, JSON и Idempotency-Key не требуются.

- Только собственное failed job допускает повтор.
- queued, running, succeeded: 409, `job_not_retryable`.
- Недостаточный баланс: 402, `insufficient_credits`, failed остаётся failed.
- Успешный повтор: 200, прежний ID, queued, attempts=0,
  error_code=null, result=null. Списывается сохранённая стоимость job.cost.
- Изменение состояния, баланс и новая charge-запись атомарны.
- Следующая окончательная ошибка возвращает оплату нового цикла один раз.
- Два конкурентных retry одного failed job: один 200, другой 409,
  списание одно. Повторный HTTP-запрос к уже queued job получает 409.

## Список и заметки

`GET /v1/jobs?status=failed&limit=20&offset=0`:

- Только задания текущего tenant.
- Фильтр применяется до LIMIT/OFFSET.
- `total` — количество после фильтра, до пагинации.
- Порядок: created_at DESC, затем id DESC.
- limit 1–100, offset >=0; неизвестный status: 422.
- `note_count` — число заметок задания, включая 0.
- В list-ответе нет text/result/notes; обязательные поля — `JobSummary`.
- Для страницы 20 не более пяти SQL-запросов, включая авторизацию.
- ORM не загружает больше limit объектов Job для одной страницы.
- Пагинация и подсчёт выполняются в БД, не на полном списке в Python.
- Приведи EXPLAIN PostgreSQL и обоснование нужных индексов в отчёте.

`GET /v1/jobs/{id}` возвращает полное задание с заметками.
`POST /v1/jobs/{id}/notes` принимает непустой text до 1000 символов,
возвращает 201 и новую заметку. Эти операции не меняют баланс.

## Миграции

`alembic upgrade head` должен работать с пустой базой и со схемой `0001`.
Миграция сохраняет существующие задания, клиентов, заметки и ledger.
Нельзя менять уже применённую `0001` или пересоздавать базу.
Модели и миграции должны согласовываться на PostgreSQL.
Испорченные исторические балансы из уже случившихся инцидентов
не нужно угадывать и молча исправлять; опиши процедуру сверки в отчёте.
